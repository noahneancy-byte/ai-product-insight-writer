# AI 产品深度研究与长文工作流

当任务涉及当前产品能力、多版本资料、创始人访谈、深度体验、竞品对照或长篇文章时读取。以下规则补充主流程，不替代用户已经确认的观点和结构。

## 1. 建立版本与证据地图

先记录事实截止时间，并按日期、地区、使用端、产品形态和可识别版本拆开材料。不要把旧版体验、开源框架、移动端、网页端、国内版和海外版默认视为同一个产品。

| 材料类型 | 可以支持 | 不能单独证明 |
|---|---|---|
| 当前官方产品与文档 | 公开功能、流程、价格和产品承诺 | 留存、实际效果和用户满意度 |
| 创始人访谈与公开信 | 产品意图、问题定义和未来假设 | 功能已经实现或结果已经成立 |
| 作者亲历 | 特定时间、版本和路径中的真实体验 | 全部用户都如此 |
| 第三方体验与用户反馈 | 可观察案例、体验上限或下限 | 整体市场结论 |
| 历史页面与旧报道 | 当时的定位和能力 | 当前产品仍然相同 |

资料冲突时，先判断是版本演进、地区差异、产品形态不同还是公开口径矛盾，再决定能写到什么程度。来源必须直接支持相邻判断；优先使用原始、官方和当事人资料，不编造标题、链接或出处。

## 2. 把亲历变成可用证据

记录体验日期、使用端、关键路径、用户动作、系统反馈、停下的位置和替代产品。需要追问时，每个问题对应一个证据缺口，优先获取以下信息。

- 用户做了什么，而不只是怎样评价
- 原本期待什么，实际得到了什么
- 为什么继续、犹豫或放弃
- 哪个细节改变了用户判断
- 类似产品采用了什么不同机制

把亲历写成特定版本中的证据，并与官方承诺、产品机制或其他案例交叉验证，不把个人观察扩大成市场定论。

## 3. 压力测试核心观点

遇到强判断时依次检查：支持证据、最强反例、替代解释、现有材料最多支持的范围，以及哪些数据会推翻判断。

把零散观点组织成“根因 → 产品机制 → 用户行为 → 产品结果 → 商业结果”的因果链。区分根因与表象；无法服务核心判断的材料，不因已经收集就强行写入大纲。

保留作者立场，但根据证据强度选择“已经证明”“公开材料显示”“作者体验发现”“可以推断”“尚未证明”等准确表述。

## 4. 管理长文的信息预算

为每章建立信息契约。

- 本章回答什么问题
- 新增什么事实、机制、判断、边界或行动
- 需要什么证据
- 最强反方或适用条件是什么
- 阶段性结论怎样引出下一问

字数预算只用于控制比例，不用于填满篇幅。材料不足时补研究、询问亲历、合并章节或缩小范围。不要用功能罗列、相似案例和主观点改写扩充字数。

维护文章工作账本：一句话主观点、完整因果链、版本口径、证据与反证、已收窄判断、章节新增结论、已经使用的案例和待回答问题。

## 5. 使用竞品作为替代机制

不要把一个早期竞品写成成功答案。比较它如何改变价值出现的顺序、Context 产生方式、授权边界、真人接管点、北极星指标和付费关系，并继续检查它是否只是提供了更清楚的假设，而非已经证明结果。

## 6. 把建议写成可验证实验

让建议追溯到前文根因，优先形成以下关系。

> 问题 → 改动 → 对照与实验 → 主指标 → 次要指标 → 保护指标 → 失败后的解释

没有可靠基准时不要编造数字门槛。区分完成注册、看到价值、建立信任、授权代理、产生真人结果和重复付费，不用供给数量或 AI 互动量替代最终价值。

## 7. 给结论设置可证伪条件

对重要批评说明成立条件、适用边界，以及哪些用户行为、数据或产品变化会让作者改变判断。可按以下链路组织证据，但不要求每篇单独成章。

> 首次可信价值 → 用户自愿补充 Context → 批准受控代理 → 产生真人或任务结果 → 再次使用或付费

“尚未证明”不等于“永远做不成”。不要用一次体验替产品下终局判断，也不要用注册量、分身数、模型调用量或概念热度替代结果证据。

## 8. 可选配图阶段

只在用户要求时执行，并放在正文和核心观点稳定之后。先列出放置位置、要表达的观点、视觉隐喻、画面比例、标题安全区和禁止元素。

组图保持统一风格，但每张承担不同论证任务。默认不在生成图中直接写长标题，避免文字变形；生成后检查构图、尺寸、文字、Logo、水印、人物异常、文件名和下载链接。封面与正文图的风格可以不同，但都应服务文章判断，不只作为科技感装饰。
